ProofPool · protocol walkthrough

How we prove a live human authorised a swap

Five parties, two HMACs, and one signature that never touches the chain until the user sends it themselves. Here is what each moving part is actually defending against.

The job

A swap should cost 0.05% if a live person authorised it and 0.30% if nobody did. So we need a token the wallet can carry to the pool that says a human was present — one that can't be copied, can't be reused forever, and doesn't leak who that human is.

Everything below exists to close one specific hole in that sentence.

Who's involved

UserA person with a phone and a wallet. Pays their own gas.
ClientThe web page in their browser. Assumed hostile — it can send us anything.
ServerOur backend. Holds the secret and the signing key. Never sends a transaction.
WorldWorld App does the face check; World's API says whether a proof is genuine.
BlockchainOur contracts: the hook that prices the swap, plus the oracle and registry it consults.

The flow

Steps 1–3 happen before the camera opens. Steps 12–14 are the only part that costs gas.

Step by step

01

The client asks for a challenge

The server chops time into fixed windows — epochs — and returns HMAC(secret, epoch). Note what is not in there: nothing about the user. Everyone who asks during the same hour gets the same value. It is unguessable to anyone without the secret, and that is its only job.

02

The client binds its own address into the signal

It builds signal = address + ":" + challenge. World ID lets an app attach an arbitrary signal to a proof, and the proof commits to it cryptographically.

03

The user takes the Selfie Check

The only step a machine cannot do. World App returns a proof containing a hash of that signal, plus a nullifier — a stable identifier for this person and this action.

04

The server checks the binding — before it talks to World

It recomputes hash(address + challenge) for the current and previous epoch and compares against the proof. One comparison, two answers: the proof was issued for this address, and it came from a still-live epoch. The matching epoch is remembered, and everything downstream derives from that one.

05

World confirms the proof is genuine

The result object is forwarded byte for byte. World answers one question only: is this a real proof? It does not know or care which address we are about to act on — that was step 4's job.

06

The server derives a nonce and signs

nonce = HMAC(secret, nullifier + matchedEpoch), then an EIP-712 signature over {subject, validUntil, nonce}. The server hands this back and stops. It never submits a transaction and holds no ETH.

07

The user swaps, carrying the attestation

The contracts recover the signer, check it hasn't expired, and ask the registry how many discounted swaps this attestation has left. If everything holds: 0.05%. Otherwise the swap still succeeds — it just pays 0.30%.

Why each piece exists

Each of these is a hole that a simpler design leaves open.

Problem

A World proof never expires

It's a bearer token. Verify it once and hand out a discount, and the user can save that proof and replay it forever. One selfie buys unlimited discounts, and "a live human authorised this swap" becomes a lie the first time it's reused.

Solved by HMAC #1 — the challenge

Time is cut into epochs, each with its own unguessable challenge folded into the signal. A proof minted in epoch 5 carries epoch 5's challenge. In epoch 7 it no longer matches anything, so it buys nothing.

Like: a hostage photo holding today's newspaper. The paper doesn't prove who they are — it proves when.

Problem

World tells you a proof is valid, not who it's valid for

Under the v4 model you forward the proof verbatim; there is nowhere to say "and I'm about to act on address B". So a client can take someone else's perfectly genuine proof, submit it alongside its own address, and a naive backend registers the wrong person.

Solved by the signal comparison

The address is inside the signal, so it's inside the proof's hash. The server recomputes that hash itself and rejects any mismatch. World never has to know about it.

Like: a concert ticket with a name printed on it. The door checks the name against your ID — not just that the ticket is real.

Problem

The nullifier is a permanent name tag

It's the same value every time that person verifies. Put it on-chain and you've published a durable identifier — anyone can now watch that human's swaps forever, across every wallet they ever verify.

Solved by HMAC #2 — the nonce

The chain sees HMAC(secret, nullifier + epoch), never the nullifier. Without the server's secret you cannot go from one to the other, so learning someone's nullifier tells you nothing about their on-chain activity.

Like: a coat-check number instead of your name. Perfectly useful to the cloakroom, meaningless to a stranger reading it over your shoulder.

Problem

A random nonce would make the swap cap meaningless

The obvious move is a fresh random nonce per verification. But then replaying the same proof produces a different nonce, a different digest, and therefore a brand-new allowance with zero swaps used. The cap would be decorative.

Solved by deriving instead of generating

The nonce is a pure function of the nullifier and the epoch. Replay the same proof and you rebuild a byte-identical attestation — same digest, same swaps already spent. Re-verifying does not top you up.

Like: a punch card. Show it again and it's the same card with the same holes in it, not a fresh one.

Problem

Deriving from "now" would undo all of the above

If step 6 used the current epoch instead of the one the proof came from, then replaying an epoch-5 proof during epoch 6 would derive a different nonce — and hand over a fresh allowance. The exact thing the challenge was built to prevent.

Solved by carrying matchedEpoch forward

Step 4 records which epoch the proof actually matched, and step 6 derives from that. The two HMACs stay locked to the same window. This is a one-word change away from being broken, which is why it's commented so heavily in the code.

Problem

The server holds a signing key

It can mint attestations. If it's compromised, what does the attacker get?

Bounded by design, not by trust

The key only signs a statement; the user submits it and pays their own gas. The server holds no funds and sends no transactions. A stolen key grants unearned discounts on one pool — it cannot move anyone's money — and rotating the trusted signer invalidates every outstanding attestation at once.

What this does not claim

Verification proves a live human authorised this swap. It does not prove the wallet belongs to a unique person — nothing stops one human verifying ten different addresses, and a selfie-level credential could not back that claim anyway. It also doesn't prove a human executed the swap: someone can verify and then let a script spend the allowance, which is exactly what the swap cap is there to bound.
